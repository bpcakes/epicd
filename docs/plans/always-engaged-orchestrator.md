This ExecPlan is a living document. Keep Progress, Surprises & Discoveries, Decision Log, and Outcomes & Retrospective current. ## Purpose / Big Picture

Epicd should be a persistent engineering lead: it understands a Beads epic, assigns implementation and independent review, investigates failures, changes tactics, and delivers verified local commits. The orchestrator is `gpt-6-astra` and chooses the work. A small deterministic safety kernel owns authority, records evidence, and rejects actions that violate the delivery contract. This model requirement applies to orchestration through both SDK and native Herdr runtimes; implementation, review, and specialist models remain separately configurable.

After this change, a failed browser test can lead to a diagnostic conversation, inspection of a declared local fixture, authorized fixture creation, and successful revalidation within the same run. A verifier that generates tracked receipts loses eligibility to approve that attempt; the orchestrator can inspect the receipts, preserve evidence, replace its workspace, and continue. Neither incident is automatically a terminal run failure. These behaviors must work with direct SDK sessions and Herdr-managed Codex agents.

The central distinction is between **delivery strategy**, which the model chooses, and **operation correctness**, which code enforces. Claim, implement, review, commit, verify, and close remain visible activities and prerequisite relationships. They no longer select the next operation. The model may insert inspection, diagnosis, replacement, validation, or waiting at any point. It cannot remove the proof required to publish a commit or close a task.

## Surprises & Discoveries

In the first kernel-mediated browser acceptance, the exact-revision reviewer needed the original diagnostic outcome and exact implementer handoff instructions. They existed in SQLite, but ordinary action-context inspection previews stopped at 1500 characters and older request arguments fell out of the bounded history. Another reviewer's recollection did not supply the missing primary records. `inspect_action` now pages the retained redacted request/result without replay, and the latest page survives context clipping. This is a generic evidence-transport correction, not a browser-specific recovery sequence or authority upgrade.

The fresh run retrieved those primary records and obtained approvals, but two reports were correctly rejected for citation scope. One put the historical diagnostic in `validationEvidenceIds`; another resolved a historical finding absent from its current open-finding batch. The review context now explicitly scopes those fields to `reviewContext.validation` and `reviewContext.findings`. Historical records belong in explanatory prose, not in those authority-bearing ID arrays. No allowed ID, approval predicate or finding was changed to accept either rejected report.

The native receipt run exposed a maintenance/admission race: action `23d9d7db-a343-4b9c-99d0-72754f686771` requested a tracker commit at control version 231. While its read-only ownership check awaited I/O, coordinator retirement incremented that version. Observations 1857–1859 record retirement, the dispatch conflict and rejection, respectively. This is not evidence that stale-authority guards should be removed. The loop previously waited for provider attempts but not for an external action's asynchronous pre-dispatch check before starting maintenance.

The receipt fault fixture found that revoking a contaminated reviewer also made its retained copy unreadable to `inspect_repo`. Diagnostic access now admits quarantined copies only with exact turn and workspace-I/O stop proof; ordinary work, capture and reassignment still refuse them. A first authenticated SDK run recovered using a fresh independent review and reached actual-SHA verification, then failed when context rollover attempted coordinator materialization during publication. Both workspace reservation and materialization had excluded coordination as if it were worker work. The new held-publication regression reproduced that error before the fix; it now proves fresh immutable coordination remains possible while mutable coordinator reservations, worker materialization, worker turns and candidate capture remain excluded.

The first actual caller-pane native acceptance failed before model startup because bootstrap froze npm's `bin/codex.js`, which has no adjacent native code-mode host. The installed current npm launcher resolves an optional native package; bootstrap now resolves that same selected installation's payload without executing the shim or substituting another installation. The next run reached application commit and exact-revision review, then failed after 32 decisions because 78 pending native observations exceeded the 64 KiB snapshot cap even after summary clipping. All 28 turns stopped; the run and evidence remained intact. Metadata itself needs byte-bounded prefix paging. The successful fresh run exercised two such pages and reached completion with a maximum frozen snapshot of 65,528 bytes.

A first paging regression woke on the coordinator's own post-snapshot bookkeeping. Waiting now short-circuits only for a backlog declared by the frozen decision input; its immediate deadline survives restart. A separate read-only probe found that a schema-valid validation-plan request could occupy 81,039 bytes in an action preview. After the live run stopped, context hardening preserved the latest action identity/result separately when request arguments must be omitted. Neither fix changes retained observations/requests, authorizes effects, replenishes budgets or enlarges the cap.

The failed SDK fixture's retained model cache reports Astra `context_window: 272000`, `max_context_window: 872000` and an effective percentage of 95; the transcript reports a 258,400-token effective window and contains no compaction record. These are observed Codex runtime values, not the current [public Astra API window of 1,050,000](https://developers.openai.com/api/docs/models/gpt-6-astra). The confined profile does not override [automatic compaction defaults](https://learn.chatgpt.com/docs/config-file/config-reference). The precise provider/runtime failure to compact is unproven; do not infer an effective Codex limit from the API page or replace native transports with Responses API compaction. Independent byte/turn maintenance is necessary even when usage telemetry is absent. In the new successful run, all nine rollovers were triggered by retained byte pressure and reported coordinator input peaked at 165,112 tokens.

The clarified reviewer contract eliminated the live approval contradiction: task pre-commit review, task actual-SHA verification and final epic review each returned `approved`, intact source and `requiredChecks: []` on their first attempt. The next live failure was context exhaustion, not approval: after 65 recorded decisions, Codex reported that the coordinator's context window was full. Its last successful turn reported 892,438 input tokens. The single coordinator conversation had accumulated repeated bounded snapshots; limiting each snapshot to 64 KiB does not bound the conversation. ## Context and Orientation

Epicd is a TypeScript ESM CLI using Node.js 22.12+, Zod for data validation, `better-sqlite3` for local durable state, and Vitest for tests. `src/bootstrap.ts` creates a configured run. `src/cli.tsx` constructs `OrchestratorController`; `src/controller.ts` registers kernel capabilities, reconciles recorded work and runs the model-led loop. `src/tui/run-view.tsx` renders the journal projection from `src/status.ts`. There is no version-1 JSON compatibility surface.

The old `src/engine/engine.ts` and its automatic next-phase methods have been deleted. `src/orchestrator/loop.ts` obtains decisions through `ControlledDecisionSource`, and `src/kernel/actions.ts` admits and dispatches the chosen capabilities. Delivery prerequisites are enforced by the capability handlers and durable journals; they are not a replacement scheduler.

Git mechanics now live in the workspace, kernel-Git, commit and publication adapters; Beads mechanics live in `kernel-beads.ts`, `tracker.ts` and `tracker-journal.ts`. The old `git.ts` and `beads.ts` adapters were removed. `src/adapters/store.ts` owns immutable run identity, settings, events, leases, quarantine and administrative writes, with delivery authority in its composed journals. Database ownership tokens alone still do not stop already-running external processes.

`controlled-sdk.ts` and `controlled-herdr.ts` implement the two runtime transports, using agent/turn journals and `controlled-launch.ts` for identity and supervised launch records. Herdr remains a native TUI transport. `src/adapters/runtime.ts` now contains event types, and `src/adapters/codex.ts` normalizes SDK events; neither is an alternate dispatcher. `sandbox.ts`, `codex-launch.ts` and `validation.ts` provide the confined process paths. A return from the generic `src/util/command.ts` is not arbitrary-descendant stop proof.

An **action** is a specific request such as starting a turn or committing a candidate. A **decision** is the orchestrator's short explanation plus one action. An **observation** is a recorded external event or measurement. A **candidate** is an immutable proposed application tree associated with a task and baseline. **Evidence** is a kernel-recorded observation of validation or independent review bound to that candidate. A **workspace generation** distinguishes a newly created checkout from one previously occupying the same role. **Reconciliation** means checking external state after an interruption before deciding whether an earlier action happened.

Keep provider-specific details in adapters.

Replace `EpicEngine` with a single CLI-facing orchestrator bootstrap under the controller lease. It starts observation and scheduling and invokes the persistent loop. The kernel schedules admitted work and drains outcomes but never synthesizes the next delivery action. Startup/recovery can reconcile already-authorized operations, stop owned processes, revoke evidence and drain recorded cleanup without a model: those actions preserve commitments and constraints rather than selecting delivery strategy. The phase-driven dispatcher must not remain an alternative workflow.

Each loop iteration assembles the current task graph, delivery facts, admissible capabilities with denial reasons, outstanding findings, running agents, unconsumed observations, memory, and remaining budgets. The model returns one action. The kernel records the decision and admission outcome, executes or schedules it, and sends the result back. An agent-start action returns an operation handle promptly; the controller continues receiving events while that agent works. There is one orchestrator decision in flight and at most one active turn per agent instance.

Persist all relevant events; coalesce ordinary event wakeups over 250 ms and check running-operation health at least every 30 seconds. Safety enforcement does not wait for a model response. A detected protected-path mutation invalidates that operation's evidence and requests interruption immediately. Its diagnostic event wakes the orchestrator to choose recovery. File watchers are wakeup hints; snapshots taken before and after stopped operations are the authority. Never treat file-watch coverage as complete attribution.

An explicit `wait_for_events` action records an event cursor and optional deadline. Sleep without repeated model calls until new relevant evidence, user input, completion, or the deadline arrives. Memory changes, audit entries, and the orchestrator's own wait bookkeeping do not wake it recursively. A hung worker, a lost runtime connection, and elapsed time without output are observations with unknown causes, not proof of agent failure.

### Action API

Implement every action below as a narrow variant with Zod validation. Inspection actions can return bounded file ranges and artifact references; none exposes arbitrary SQL, unrestricted host shell, raw Git commands, or a setter for lifecycle state.

`inspect_observation` reads an exact observation ID within the current run, including an already-acknowledged or shortened observation. It pages the immutable retained JSON record with UTF-16 `offset`, a positive `limit` up to 4000 characters, `totalCharacters` and `nextOffset`. Foreign/absent IDs and out-of-range offsets are rejected. The latest requested page remains available in context even under byte pressure; earlier previews can be omitted. The stored summary may itself be partial/redacted, and neither a complete retained record nor its artifact references grant authority or supply verification evidence.

`inspect_action({ actionId, offset, limit, expectedDigest })` reads this run's retained action request and outcome. Start at offset zero with a null digest; continuation pages require the returned SHA-256 digest of the fully redacted view. A changing running action requires restarting the read, never joining pages from different outcomes. Limits are 1–4000 UTF-16 characters. The latest `inspect_action` or `inspect_observation` page survives the ordinary 1500-character preview limit, including under the 64-KiB context cap. It does not replay an action, expose a controller authority token, or turn a diagnostic/agent claim into verification. Redaction is best-effort and pages are text views, not a new machine-authoritative action record.

`run_diagnostic_check` accepts an existing candidate and plan identity, its registered immutable review/verification workspace generation, and one bounded `RequiredCheckSchema` command without a caller-selected stage. The kernel derives the stage from the workspace binding. It uses the same supervised execution, source-integrity checks and separately authorized service/fixture bindings as required validation. The durable record freezes `purpose: diagnostic`, the command and digest, candidate/revision and outcome. Diagnostic success never satisfies or shadows a required delivery check, including one with the same ID or command; reconciliation never reruns it or upgrades its purpose. Capture stopped implementation source before diagnosis, then recapture after a subsequent implementation turn before seeking delivery evidence. No fixture name, failure string or next action is prescribed by this capability.

`inspect_run` returns authoritative delivery facts, captured tracker observations, budgets, operations, agents and diagnostic metadata. `inspect_repo` implements read, literal search, recursive list, source diff and baseline history within a ready registered workspace generation. It ignores mutable index/HEAD when comparing source to the baseline. File diffs return paged before/after content rather than minimal unified patches; links expose their value, never target contents. Inspect a surviving parent to see deleted-directory entries. `inspect_agent` returns assignment, turn state and available reports. `inspect_artifact` now reads a run-scoped immutable diagnostic ID with bounded redacted character pages, explicit source/local gaps, content digest and non-evidence labeling. It is not arbitrary file access. `inspect_fixture` remains to be implemented through a typed declared-resource provider.

Repository read offsets count zero-based UTF-16 characters in the fully redacted view; other operations page rows. Use returned `nextOffset`, not an inferred page size. Read pages accept at most 1000 characters; row pages at most 1000 rows, with retained JSON at most 64000 bytes and row-text previews at most 4000 characters. Files are bounded to 4 MiB, source scans to 32 MiB, 10000 entries and 64 nested directories. A 30-second cooperative cancellation signal reaches filesystem traversal and Git subprocesses; it is not a hard deadline for a stalled host filesystem call. Unsafe paths, provider/Git metadata, shared regular files and special-file content are rejected. Recognized credential paths are excluded from content reads and secret-pattern redaction precedes paging; this is not a guarantee that every possible secret is recognized. Search and diff line coordinates describe the redacted view. Pages may observe different source states during concurrent work and never produce validation, candidate, approval or restoration authority.

The implemented delivery registry also supplies `inspect_candidate`, `inspect_validation_plan`, and `inspect_evidence` by run-scoped identities. Candidate inspection omits the full manifest, plan storage is bounded to 32 KiB, and evidence inspection bounds serialized diagnostics without exposing controller lease identity. The independent review registry adds `inspect_review`, character-paged `read_review`, and ledger-paged `inspect_findings`. An inspection preview may be shorter than the retained evidence row; it never upgrades truncated execution output to passing evidence.

The tracker registry supplies `refresh_tracker`, `export_tracker`, `inspect_tracker`, `read_tracker_issue`, `inspect_tracker_operation`, and `reconcile_tracker_operation`. Captures are bounded to 1000 issues and 4 MiB, with a whole-capture deadline; oversize or inconsistent graphs fail without accepting a partial result. Issue pages label advisory readiness and truncated fields, and full field reads pin the exact immutable snapshot ID. `request_beads_transition` implements claim/adopt with a null revision and task/container/root closure with distinct exact-publication and scope proofs; `complete_run` additionally checks live graph/ref state, a published closed-scope tracker export and stopped resources. Custom workflow statuses, routed/external identifiers, non-Linux execution, and unrecognized storage layouts fail closed rather than silently falling back to legacy behavior.

### Admission, ordering, and durable effects

Every mutation validates the current lease, control version, action's target IDs/generations, effective policy digest, relevant workspace/candidate identity, and current external preconditions. `controlVersion` increments on authoritative changes such as task ownership, candidate replacement, revocation, settings, or pause; it does not increment for every log fragment. An action based on a stale control version is rejected with fresh context. Inspection can read stale history explicitly, but that history cannot authorize a mutation.

Create an action intent and its audit event in one SQLite transaction before starting an external effect. Persist states `accepted`, `running`, `succeeded`, `failed`, `cancelled`, or `indeterminate`. Transition helpers require the lease and expected action state. Store the result, derived delivery state, evidence IDs, and completion event together. A unique `(run_id, decision_id)` plus a canonical request digest makes an identical replay return the recorded action; reusing that ID with different arguments is rejected. A deliberate retry gets a new action ID, a `retryOf` reference, and fresh guards.

SQLite and Git/Beads/processes do not share a transaction. Do not promise exactly-once execution. A crash after an effect but before recording success produces an indeterminate operation that must be reconciled. Agent creation has a persisted run/agent/turn identity before launch. Commit creation has a persisted parent, tree, and commit payload, so the same commit object can be recognized. Publishing uses ref compare-and-swap. Claims reconcile through authoritative owner/status. Closure records contain the task, verified revision, and expected transition. Fixture provisioning has a provider-owned resource identity and an inspect operation. Validation interrupted without a durable exit result is incomplete and must be rerun if policy permits.

Use a single logical scheduler for external mutations. An implementation writer owns its workspace until its process tree stops. Validation and review may run in separate candidate copies; review approval or commit creation for a task cannot race an implementation turn on that task. Fixture users hold a fixture-use record so provisioning or reset cannot race a test. Inspection and distinct diagnostic workspaces may run concurrently. Lease loss prohibits further effects, requests cancellation, and prevents late completions from becoming evidence. A new controller reconciles surviving workers before launching replacements. A database lease alone does not stop the old workers.

On a persistence failure, unsafe state, lost lease, or unknown ownership of a live process, stop affected work without consulting the model. Preserve uncertainty. Ordinary command failures, rejected actions, invalid model output, exhausted local attempts, and worker-runtime unavailability are typed problems fed to a healthy orchestrator while authority remains intact. A failed action is not a failed epic.

Coordinator-runtime failure requires a separate bounded execution rule: an unavailable Astra cannot diagnose its own unavailability. Normalize structured provider failures where supplied; distinguish retryable transport/rate/overload failures from authentication, model access, invalid configuration, and exhausted billing/quota. HTTP 429 alone does not establish retryability. Honor an available `Retry-After` without exceeding the run's waiting policy; never alter credentials, billing, or project limits automatically. Unknown native screen errors remain unclassified diagnostics, not invented API error codes. [Provider error distinctions](https://developers.openai.com/api/docs/guides/error-codes).

A provider safety-monitoring stop is a separate nonretryable condition. Preserve the notice, revoke the attempt's result authority, and request operator review; do not automatically create another session to continue the stopped task. Current Codex guidance says findings/resume availability differs by surface and that a CLI task can end without a resume flow. Runtime normalization must use an actual structured notice when available; absent that, preserve unknown diagnostics rather than asserting a safety classification from screen prose. [Safety monitoring and paused tasks](https://learn.chatgpt.com/docs/agent-approvals-security#safety-monitoring-and-paused-tasks).

For the first implementation, permit at most three transport attempts for one issued decision, with cancellable backoff starting at two seconds and capped at thirty seconds; a longer provider delay records a deadline instead of spinning. Persist attempt count and next eligible time before retry, maintain lease/worker health while waiting, and never replenish the allowance through restart or context rotation. Reuse the pending ticket only while its cursor, control version, policy, and coordinator generation remain valid. Retire a superseded attempt and reject its late response. One logical decision is charged once; record every transport attempt and any observed usage separately. Invalid structured model output still follows the existing bounded decision-feedback path.

On a nonretryable failure or exhausted transport allowance, record one runtime escalation without asking the unavailable model to produce it. Stop new delivery admissions, settle or interrupt existing workers under the pause contract, preserve findings/resources, and enter `awaiting_user` without switching model or legacy workflow. No task may be claimed before initial Astra preflight succeeds. This rule belongs in the decision-source/loop and durable journal integration in Milestones 2 and 4; it restores an execution dependency, not a deterministic delivery strategy.

The current implementation lives in `src/domain/decision-source.ts`, `src/adapters/decision-journal.ts`, and `OrchestratorLoop`. Database version 5 adds `decision_executions` and `decision_source_attempts`, including raw quarantine and pre-upgrade snapshot coverage. `prepare()` freezes a digest-checked context at most 64 KiB before `start()` commits a dispatch and its observation. `finish()` records a bounded/redacted outcome and deadline under the dispatching controller lease. Retries reuse that input even when new observations arrive; those observations remain unconsumed for the next decision. Control/policy changes invalidate dispatch, and cached decisions still pass normal action admission. A durable response can be replayed at the final decision-budget slot instead of incorrectly asking for another model call.

`DecisionSourceError` is a trusted adapter contract asserting a settled request, not an error classifier for model prose. Only its `transient` code permits an automatic retry. The default delays are two and four seconds for the remaining attempts; automatic backoff is capped at thirty seconds. A longer provider delay becomes a cancellable persisted deadline, up to a 24-hour harness bound; longer waits require operator direction. Unknown exceptions or controller loss leave an unsettled exclusion across tickets and restart. Independent health monitoring requests cancellation on lost authority even if the source promise does not settle. The controlled SDK source records generic but confirmed-stopped failures as nonretryable `runtime` failures; it does not classify embedded provider prose as an authentication, quota, safety, or transient code. Available normalized usage/events are journaled. Do not cast legacy generic SDK/Herdr exceptions into a settled-error type merely to enable retries.

### Evidence and non-negotiable delivery prerequisites

A candidate record includes `candidateId`, generation, task ID, parent commit, full tree hash, application tree hash excluding `.beads`, workspace generation, capture manifest, policy digest, and validation-plan ID. Capture only after the writer stops. Record bytes and modes for tracked and eligible untracked application files, symlinks, deletions, and renames using NUL-delimited Git output. Reject unsupported submodules, LFS/filter materialization, or other layouts in preflight until their exact-copy contract is implemented and tested; do not silently omit content. Use Git object IDs as opaque strings, not fixed 40-character assumptions.

A validation plan contains named required checks and acceptance criteria from the frozen repository declaration, the task, and independently raised findings. Kernel-enforced required checks come from explicit structured policy. The orchestrator can add checks; it cannot remove or weaken required checks or substitute `true` for a required command. Free-form acceptance criteria still require reviewer judgment: the kernel can prove that specified checks ran against specified bytes, not that arbitrary business requirements have been mathematically proven.

Where no repository check declaration exists, the orchestrator proposes a nonempty plan from repository instructions and task criteria, and an independent reviewer must accept its adequacy before approval can be issued. This remains a judgment-based coverage check, visibly distinguished from operator-declared mandatory commands. Reviewer-requested additions become requirements in the next plan version. The kernel must not manufacture a meaningful-test guarantee from a command name or a successful exit code.

Agent reports are claims. `ImplementationResultSchema` and `ReviewResultSchema` remain useful input formats, but reported `tests` alone cannot mint passing validation evidence. `ValidationEvidence` records the kernel-launched command/check ID, command digest, actual exit status, start/end times, workspace/candidate identity, relevant environment/fixture generation, and output artifact references. Missing, failed, cancelled, skipped-required, truncated beyond interpretable output, and unknown results never satisfy a required check. A later retry can supersede a specific failed check with a pass for the same required check and current environment; history is retained. A new failed result revokes eligibility until resolved.

`ReviewEvidence` identifies the reviewing agent and turn, candidate generation, base and tree, result, findings, and validation references. A reviewer cannot have served as an implementer or repair writer for this task. Do not give a fresh reviewer the implementer's private conversation or another reviewer's verdict as an instruction to approve. Give it the task, repository instructions, factual evidence, diff, and relevant prior findings for targeted repair review. Replacements inherit unresolved findings, so replacing a reviewer cannot erase them. The kernel preserves the finding ledger; resolution requires suitable independent review evidence, not the coordinator deleting an array.

Committing requires a current independent approval, all required pre-commit checks, no unresolved findings, a stopped writer, and the exact approved full tree/parent. Use a temporary index and inspect its tree; never trust arbitrary staging left by an agent. Post-commit verification uses a fresh agent at the actual candidate commit SHA, with its own required validation evidence. A synthetic snapshot used for pre-commit review is explicitly labeled as such and cannot count as exact-commit verification. Post-commit fixes produce a new candidate and follow-up commit; no automatic amend or history rewriting.

Publishing requires current exact-commit verification and imports the identical object, preserving its SHA. Closing a task additionally requires that published verified revision, fresh Beads ownership and dependency checks, and no superseding candidate or unresolved mandatory finding. Once tracker-only commits advance the delivery branch, closure retry validates the recorded verified application tree and a proven tracker-only descendant chain; it does not require current HEAD to equal the earlier application commit. This is necessary for a crash after tracker sync or a tracker commit.

The final epic review examines the exact published application state after all concrete descendants are closed. Root closure requires fresh graph evidence that no new open descendant appeared, no unresolved epic finding, and an independent final verification record. Nested containers close only after their actual descendants. If final evidence exposes a repair need, the orchestrator can start an epic-scoped repair assignment bound to the latest captured root candidate, under the existing run budgets. Its kernel-built context includes unresolved findings; model prose does not clear them. Publish a reviewed and verified follow-up commit and rerun final review. The root stays open. This supports recovery without silently inventing tracker issues or reopening user-managed tasks.

### Workspace isolation and safe recovery

Add `src/adapters/workspaces.ts` with kernel-owned workspace manifests under the private Epicd state directory. A manifest records run ID, workspace ID/generation, canonical path, purpose, baseline, owner agent/turn, lifecycle, and cleanup state. Use independently initialized or copied Git repositories with no object alternates, writable hard links, inherited remotes, executable hooks, or copied credentials. Keep read-only history needed for review. The kernel can export/import Git objects over local supervised commands; agents receive no writable path to the authoritative repository or another workspace.

Kernel Git commands use controlled configuration and environment so inherited hooks, external diff programs, credential helpers, or checkout filters cannot turn metadata operations into unrestricted repository execution. Required repository hook checks must be represented as explicit confined validation, not silently omitted. Dependency installation and build preparation are also explicit workspace operations: use the candidate's lockfiles, declared cache/scratch paths, and authorized network policy. Do not assume that copying tracked files also supplies ignored dependencies, browser binaries, environment files, or generated assets. Preparation that changes candidate source requires recapture and fresh review.

Maintain one private delivery repository. An implementation agent receives its working files under a confined profile; Git metadata, frozen policy/instruction control files, and authoritative tracker/state storage are protected. Review/verification agents receive separate copies, with mutable build/scratch output but immutable candidate source. Commands that try to append tracked receipts should fail at the source boundary; if an adapter can only detect such a change, that attempt is ineligible for approval and its workspace is quarantined. Do not describe post-hoc detection as prevention. Runtime capability admission distinguishes these protections.

For the initial release, require source immutability during accepted review/verification, not merely equality before and after: a verifier could edit a test, run it, and restore it. Prefer a read-only candidate plus explicitly writable scratch/build paths supplied by the repository declaration. If a test tool requires a tracked-path write, run it as diagnostic work in a disposable mutable copy, then rerun an equivalent approved validation that preserves candidate source before accepting evidence. Receipt paths are not automatically exempted because their names resemble logs.

The selected repository remains the source of the initial baseline and the live Beads database. Local delivery uses a run-owned branch that is never checked out by Epicd. Before every branch advance, verify the ref is not checked out in any worktree and still equals the recorded previous value; otherwise return an ownership conflict. Do not apply patches, reset, clean, stash, or switch the user's working tree. Tracker operations may update `.beads` through its authoritative adapter as already authorized by starting a run; tracker-only objects on the delivery branch are constructed with an isolated index and cannot stage unrelated user changes.

`restore_owned_delta` is legal only in a disposable managed workspace with a known generation, a complete baseline, a stopped process tree, and no detected user intervention. Fingerprints establish expected bytes; confinement plus exclusive workspace ownership establishes the scope that may be replaced. A changed canonical checkout, a managed tab that the user took over, or unknown writers is an ownership problem requiring preservation and user direction. On ambiguous provenance preserve the whole workspace. For known disposable scratch, preserve redacted receipt/output artifacts first, then regenerate the copy from the immutable candidate.

Workspace deletion is a durable cleanup operation. Validate canonical paths and manifests, refuse symlink escapes and unregistered directories, and never delete while a process may still write. Do not reuse workspace IDs or paths for a new generation. Cleanup failure after delivery leaves a complete, non-owning run with reachable cleanup intent, matching the existing product's behavior.

## Idempotence and Recovery

`reconcile_action({ actionId })` now exposes the six core delivery inspectors through `src/kernel/delivery-recovery.ts`; cold bootstrap uses the same `reconcileDeliveryAction()` and parent-settlement helper. The stored original action and operation identity select the inspector, not model-supplied resource fields. Live or accepted actions cannot be reconciled. Durable capture/copy/validation/review/commit results may settle historical acknowledgements, but grant no fresh approval. Failed validation remains failed; an unrecorded stopped review verdict is discarded and requires a new independent review. A stopped capture without a retained snapshot fails without recapture. Unbound or changed review copies are preserved without late binding or restoration. Unknown source/inspection I/O retains its exclusion. Transient inspection failures allow another observation, never effect replay. Publication, tracker, fixture and diagnostic recovery retain their dedicated paths; `complete_run` retains its atomic terminal protocol. No storage shape or format conversion was introduced.

Repository inspection replay returns the original retained action result even if source has subsequently changed. After controller replacement, `reconcileRepositoryInspection()` accepts only an `inspect_repo` action with the journal's indeterminate status/result marker and no retained inspection payload, then settles it failed: no mutation must be undone and no new read can reconstruct its lost historical observation. A new decision may request fresh evidence. Full bootstrap must still fence authority, reject late old-controller settlement and dispatch reconciliation through the existing journal helper. Descriptor/process cleanup completes on the local action path; inspection cannot create a candidate, release a writer or justify restoration.

Task closure recovery inspects the original tracker operation after independently confirmed stop; it never sends `close` again. Reacquire read-only ref verification, inspect Beads markers, and revalidate the original claim-bound publication/review before approval. A foreign marker, owner, changed work or changed publication is preserved as a conflict, not restored. A provably unused dispatch gate can settle `not_closed` and permit a new guarded request. Inspection while paused may record physical facts but leaves the original parent action indeterminate until an active controller can approve it. `reconcileTracker()` must not translate a null outcome into parent failure; the model-facing reconciliation handler also refuses to report a pending operation as settled. Full bootstrap still needs the independent stop source for abandoned controller-owned Git/Beads I/O.

Tracker recovery is `TrackerAdapter.reconcile()` plus `reconcileTracker()` for the original action's settlement. A durable unused start gate proves no command was launched; otherwise confirmed process closure is required before inspection, including on a replacement controller. Claim/adopt effects are never replayed. A failed inspection preserves a known-stopped pending record for explicit retry, and a missing prior stop remains unknown even if Beads currently shows the expected owner. After a successful claim, refreshed owner, epic status and work fingerprint must still match before another task agent is assigned or continued. Changed requirements, reparenting or ownership require investigation and a future explicit authority/replanning path, not automatic reassignment or restoration. Full bootstrap must supply independent stop reconciliation and ongoing refresh; registering these capabilities alone does not implement either.

The same persisted decision submitted twice returns the same action result. An action whose effect may have happened is reconciled before retry. Ref updates compare the expected previous value; tracker transitions reread authority; workspace/agent generations never get reused; fixture ownership must be externally provable. No retry can waive an evidence requirement or refill its own budget.

On resume, acquire the lease, validate the exact current state, load policy, inspect workers/resource intents, reconcile indeterminate actions, invalidate superseded evidence, recover the consumed observation cursor and memory, then admit new decisions. Cleanup-only recovery need not initialize a model. If persistence is unavailable, stop admission and preserve resources; do not attempt LLM-driven database repair or old-format conversion.

Review recovery must not rerun an already dispatched review action. A finished evidence row and its immutable findings survive replay; a bound but unfinished turn needs exact process-stop reconciliation and discard of the unrecorded verdict. An admission or post-review inspection with unknown I/O still owns its workspace, including after controller lease replacement. Do not mark that operation stopped from a fingerprint comparison or from the absence of an agent process; it represents controller-owned I/O, not only the reviewer. New candidate generations invalidate approval and require independent reassessment of prior findings. Accepted required commands survive that regeneration.

Private commit recovery begins with its durable operation, raw object content, planned revision, and source I/O exclusion. `reconcileCommit()` refuses Git-only reconciliation until that exclusion has independent stop evidence; a new lease or absent ref is not stop proof. Once I/O is stopped, compare the exact object bytes and unique private ref. Record a retained matching object without rewriting it, record an absent/unretained result with explicit details while preserving any object, and preserve conflicts for investigation. New model requests cannot create a second commit for that candidate. New implementation work must use the latest retained private parent; after publication/tracker integration this must include the proven tracker-only delivery tip. There is no automatic amend, reset, or deletion of a user's checkout or an older assignment.

Publication recovery must not infer all-or-nothing effects from Git's prepared transaction. Its branch and unique receipt are separate persisted refs, and a crash can leave either one alone. The physical transport exposes that conflict without repairing it. A matching `.keep` is a retention obligation, not permission to repeat `index-pack`; an existing other-owner keep is preserved. The journal records these identities before writes, retains unknown-I/O exclusions across leases, and preserves late intervention even when subsequent ref inspection observes the target SHA. `PublicationAdapter.reconcile()` requires stopped original I/O or a provably unused dispatch gate; it reserves new inspection exclusions, compares destination refs and raw object bytes, then releases only the exact owned lock ref by compare-and-swap under a recorded release intent. A transient read/cleanup failure leaves a pending known-stopped record for explicit retry. A new attempt may inspect a stopped prior operation's retained exact pack, preserving the original `.keep` owner; it may not adopt a foreign keep. Neither a new controller nor a model may turn `observeRefs().outcome === "applied"` into a tracker closure proof by itself. Full bootstrap still needs an independent stop source for abandoned controller-owned I/O and must not manufacture one from database lease replacement.

Use fresh disposable state for development and acceptance. The hard-cut implementation never upgrades or restores an older database. Leave unsupported user databases untouched and report how to select a fresh state path; do not delete real run data as a coding step. SQLite alone cannot undo already-executed Git, Beads or fixture effects. Recovery within the current format must continue to preserve those obligations.

Deletion and fixture cleanup are limited to explicitly recorded owned resources. Published local delivery branches are retained after successful cleanup. Quarantine or cleanup abandonment preserves forensic metadata and warns that external resources may remain; neither operation authorizes deleting unrelated directories, closing unrelated Herdr tabs, or dropping a database whose owner cannot be proved.
